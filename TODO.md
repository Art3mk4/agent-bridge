Актуальный список известных ограничений и следующих улучшений.

Приоритеты:

- **P1** — заметный функциональный или эксплуатационный пробел.
- **P2** — улучшение качества, тестирования или документации.

## P0 — надёжность и стабильность

- [ ] **P0-1. Устранить race при переключении SQLite в WAL при конкурентном старте supervisor.**
  - Наблюдение: при одновременном запуске двух supervisor-процессов возможен `sqlite3.OperationalError: database is locked` на этапе `PRAGMA journal_mode=WAL`.
  - Нужно: retry/timeout для WAL-переключения и регрессионный стресс-тест конкурентных supervisor.
  - Критерий закрытия: конкурентный сценарий стабилен, полный набор тестов проходит без этого падения.

- [ ] **P0-2. Проверить активацию новой версии listener в реальном окружении.**
  - Наблюдение: уже запущенный listener продолжает работать на старом коде и не пишет progress-файл до перезапуска.
  - Нужно: контролируемо перезапустить listener и проверить `listener status`, `progress --once` и обработку безопасной задачи.
  - Критерий закрытия: status показывает `idle` или актуальную стадию, а после задачи сохраняется итог в `last`.

- [ ] **P0-3. Добавить маркер версии/возможностей listener.**
  - Наблюдение: состояние `unknown` может означать и listener со старым кодом, и отсутствие доверенного progress-файла.
  - Нужно: добавить feature/version marker в status или progress-документ.
  - Критерий закрытия: status явно различает старую версию, отсутствие progress и ошибку чтения.

## P1 — индикация и наблюдаемость

- [ ] **P1-1. Расширить progress/status безопасными метаданными сообщения.**
  - Наблюдение: lifecycle отображается, но sender, `conversation_id`, `kind` и роль сообщения в диалоге не показываются.
  - Нужно: добавить эти метаданные без текста задачи, prompt и секретов; описать контракт в README и тестах.
  - Критерий закрытия: по status видно, от кого задача и к какому диалогу она относится, без раскрытия payload.

- [ ] **P1-2. Зафиксировать границы прогресса выполнения.**
  - Наблюдение: сейчас отображается lifecycle listener/supervisor; внутренний ход worker не передаётся.
  - Нужно: либо добавить поддерживаемые этапы worker, либо явно описать, что доступен только lifecycle supervisor.
  - Критерий закрытия: README, MCP `listener(status)` и CLI `progress` единообразно описывают доступный уровень детализации.

- [ ] **P1-3. Подготовить опциональную индикацию в Claude Code UI.**
  - Наблюдение: штатной возможности внедрить внешнее событие в активную сессию нет; statusLine остаётся локальной настройкой.
  - Нужно: проверить пример statusLine из README на интервале обновления, безопасной деградации и отсутствии payload.
  - Критерий закрытия: пользователь cclocal видит компактную строку прогресса, а при остановленном listener вывод остаётся нейтральным и безопасным.

- [ ] **P1-4. Привести права runtime-лога к документированным.**
  - Наблюдение: `systemd/runtime/dispatcher.log` может создаваться с правами `0644` вместо `0600`.
  - Нужно: устанавливать права при создании и ротации, добавить проверку.
  - Критерий закрытия: новый и пересозданный лог имеют `0600`.

## P1 — эксплуатация и разрешения

- [ ] **P1-5. Документировать минимальные MCP-разрешения для headless-воркеров.**
  - Наблюдение: недостаточный project allowlist приводит к честному `blocked`, а отсутствие shell/python-разрешений блокирует инженерные задачи.
  - Нужно: отдельно описать права для обычной двусторонней задачи и инженерной задачи; добавить startup-проверку или явное сообщение о недостающих правах.
  - Критерий закрытия: отсутствие разрешений не выглядит как `uncertain` или ошибка диспетчера.

- [ ] **P1-6. Добавить безопасную процедуру разбора исторических `blocked` и `uncertain`.**
  - Наблюдение: после ручного вмешательства могут оставаться исторические попытки, ручные результаты и неподтверждённые сообщения.
  - Нужно: read-only отчёт по backlog и документированные ручные действия для каждого состояния без автоматической перезаписи истории.
  - Критерий закрытия: активный инцидент отличается от исторического следа, путь действий понятен.

## P2 — качество и тесты

- [ ] **P2-1. Добавить воспроизводимый stress/regression для конкурентных supervisor.**
  - Нужно: после исправления WAL добавить регулярный стресс-сценарий с разумным лимитом времени.
  - Критерий закрытия: race не воспроизводится, обычный полный набор остаётся быстрым и стабильным.

- [ ] **P2-2. Провести live-проверку fresh DB после обновления listener.**
  - Нужно: на отдельной тестовой БД проверить автоматический первый dispatch и создание `dispatch_attempts` без ручного `on_message.py`.
  - Критерий закрытия: сценарий подтверждён без замены или пересоздания рабочей БД.

- [ ] **P2-3. Синхронизировать README, CLI-помощь и фактическое поведение.**
  - Нужно: сверить примеры команд, JSON-поля и описание ограничений после дальнейших изменений.
  - Критерий закрытия: примеры из README выполняются и совпадают с реальным выводом.

## Инварианты

- В логи, status и progress-файлы не попадают текст задачи, prompt, worker output, токены и другие секреты.
- Нет автоматических повторов неудачной попытки.
- Терминальное состояние conversation не принимает новые `task`/`result`.
- `auto.kimi` остаётся отключённым по умолчанию до явного решения пользователя.
