## P0 — надёжность и стабильность

- [ ] **P0-1. Устранить race при переключении SQLite в WAL при конкурентном старте supervisor.**
  - Наблюдение: при одновременном запуске двух supervisor-процессов возможен `sqlite3.OperationalError: database is locked` на этапе `PRAGMA journal_mode=WAL`.
  - Нужно: retry/timeout для WAL-переключения и регрессионный стресс-тест конкурентных supervisor.
  - Критерий закрытия: конкурентный сценарий стабилен, полный набор тестов проходит без этого падения.

- [x] **P0-2. Проверить активацию новой версии listener в реальном окружении.**
  - Закрыто 2026-11-02: слушатель claude перезапущен штатно (disable → ожидание выхода по /proc → enable), новый pid, `status` отдаёт `stage=idle`; демо-задача прошла стадии `received → supervising → finished` с записью итога в `last` (`result=succeeded, duration_s=30.4`).
  - Остаток: сторона kimi — см. P1-8.

- [ ] **P0-3. Добавить маркер версии/возможностей listener.**
  - Наблюдение: состояние `unknown` может означать и listener со старым кодом, и отсутствие доверенного progress-файла.
  - Нужно: добавить feature/version marker в status или progress-документ.
  - Критерий закрытия: status явно различает старую версию, отсутствие progress и ошибку чтения.

## P1 — эксплуатация и разрешения

- [ ] **P1-5. Документировать минимальные MCP-разрешения для headless-воркеров.**
  - Наблюдение: недостаточный project allowlist приводит к честному `blocked`, а отсутствие shell/python-разрешений блокирует инженерные задачи.
  - Нужно: отдельно описать права для обычной двусторонней задачи и инженерной задачи; добавить startup-проверку или явное сообщение о недостающих правах.
  - Критерий закрытия: отсутствие разрешений не выглядит как `uncertain` или ошибка диспетчера.

- [ ] **P1-7. Разобраться с блокировками headless-воркера claude.**
  - Наблюдение: при задаче, упирающейся в действие, требующее подтверждения, воркер либо очень долго идёт до честного `blocked` (пример из README: `result=blocked in 938.7s`), либо, при диалогах не-permission типа, может остановиться навсегда — человека для подтверждения в схеме нет. Сейчас воркер стартует с `--permission-prompts none` (`systemd/on_message.py:501-502`), автоматический отказ permission ожидается, но фактическое поведение и потерянное время не разобраны.
  - Нужно: воспроизвести (задача с заведомо недопустимым действием), по `worker_*.out`/exit-коду зафиксировать, где именно теряется время; решение — явный таймаут supervisor'а и честный `blocked`/короткий notice без payload вместо висящей сессии; связать с P1-5.
  - Критерий закрытия: поведение при блокировке документировано в README; воркер не может висеть дольше заданного лимита без видимого статуса; супервайзер отдаёт честный blocked/needs_human.

- [ ] **P1-8. Снять deadline-gate с не-попытавшихся сообщений в скане слушателя.**
  - Наблюдение (подтверждено 2026-11-02): `_CONVERSATION_SCAN`/`_LEGACY_SCAN` (`systemd/listener.py:414-446`) диспатчат сообщение только пока `response_deadline > now`, а попытка разрешена ровно одна. Сообщение, пришедшее, пока слушатель выключен, перезапускается или занят воркером (дефолтный таймаут send_message — 300 с), молча становится недиспатчабельным навсегда — хотя send_message и README обещают: «response_deadline — чистые метаданные, nothing is timed, late replies stay valid». Пользователь вынужден вручную писать интерактивному cclocal, чтобы тот подхватил такие письма.
  - Нужно: убрать `response_deadline > now` из условия диспатча для сообщений без dispatch_attempts (дедлайн остаётся метаданными для воркера/человека), либо явно пересмотреть семантику и документацию; добавить тест «письмо пережило остановку слушателя дольше дедлайна и было доставлено».
  - Критерий закрытия: письмо без попыток диспатчится после возвращения слушателя независимо от дедлайна; README/send_message и поведение скана согласованы; тесты зелёные.

- [ ] **P1-9. Сделать недиспатченные письма и blocked видимыми.**
  - Наблюдение (подтверждено 2026-11-02): headless-воркер claude без write-разрешений завершает инженерные задачи только как `blocked` (msg#35 — 938.7 с, msg#45 — 337.4 с, ~$1.2 за прогон), а единственный сигнал — `last`-сегмент progress-строки. Письмо, ожидающее диспатча (сложенное deadline-gate из P1-8), вообще нигде не видно. Пользователь узнаёт о проблеме, только когда «ничего не происходит», и вручную просит интерактивный cclocal проверить почту.
  - Нужно: счётчик недодиспатченных писем агента в `progress_line` (виден и в statusline cclocal, и через MCP `listener(progress)`); при blocked — короткий notice без payload инициатору, если инициатор — тоже агент с живым слушателем; свести с P1-5/P1-7.
  - Критерий закрытия: по statusline/MCP видно и «письма лежат, но не диспатчатся», и «последняя задача ушла в blocked» без ручной проверки inbox.

- [ ] **P1-6. Добавить безопасную процедуру разбора исторических `blocked` и `uncertain`.**
  - Наблюдение: после ручного вмешательства могут оставаться исторические попытки, ручные результаты и неподтверждённые сообщения.
  - Нужно: read-only отчёт по backlog и документированные ручные действия для каждого состояния без автоматической перезаписи истории.
  - Критерий закрытия: активный инцидент отличается от исторического следа, путь действий понятен.

- [ ] **P1-7. Разобраться, почему расширенный allowlist не дошёл до headless-воркера.**
  - Наблюдение (2026-11-02, попытки 33 и 35): `vibe_coding/.claude/settings.local.json` расширен точечными правилами (`Edit/Write` в `agent_bridge/**`, доступ к `~/.claude-local`, `Bash(python3 …)`, `Bash(uv run python …)`, `additionalDirectories`), но headless-воркер, запущенный ПОСЛЕ правки, увидел прежний набор и оба раза честно вернул `blocked`. Подозрение: абсолютные пути в правилах `Edit(/abs/path/**)` могут не матчиться (паттерны обычно якорятся к project root); не подтверждено.
  - Нужно: установить причину (минимальный repro: правило `Edit(/tmp/...)` у headless-воркера), либо зафиксировать, что инженерные write/python-шаги headless не выполнимы в принципе и в текстах задач помечаются «выполняет интерактивная сессия/человек».
  - Критерий закрытия: либо расширенный allowlist реально доходит до воркера (проверено live), либо в README и шаблоне задач зафиксировано правило распределения шагов. Отдельно решить судьбу текущего расширения: оставить или откатить.

- [ ] **P1-8. Перезапустить слушателя kimi для активации progress на стороне kimi.**
  - Наблюдение: слушатель kimi (auto=false) до сих пор работает на коде до progress-изменений; его `status` отдаёт `stage=unknown`, progress-файл не пишется.
  - Нужно: штатный внешний рестарт (disable → ожидание выхода по /proc → enable) в удобный момент; проверить `stage=idle` после.
  - Критерий закрытия: `listener.py status --agent kimi` показывает `stage=idle`, а при задаче kimi — осмысленные стадии.

## Инварианты

- В логи, status и progress-файлы не попадают текст задачи, prompt, worker output, токены и другие секреты.
- Нет автоматических повторов неудачной попытки.
- Терминальное состояние conversation не принимает новые `task`/`result`.
- `auto.kimi` остаётся отключённым по умолчанию до явного решения пользователя.
- Рестарт слушателя — только внешняя операция (disable → выход процесса → enable); из диспетчеризованного воркера он архитектурно невозможен (мёртвая петля ожидания).
