## P0 — надёжность и стабильность

- [x] **P0-1. Устранить race при переключении SQLite в WAL при конкурентном старте supervisor.**
  - Наблюдение: при одновременном запуске двух supervisor-процессов возможен `sqlite3.OperationalError: database is locked` на этапе `PRAGMA journal_mode=WAL`.
  - Причина (воспроизведено детерминированно): пока файл не в WAL, `PRAGMA journal_mode=WAL` при чужой RESERVED-блокировке падает сразу, `busy_timeout` для этого запроса не используется. `on_message._connect` переключал режим без повторов (в `server._init_db` повторы были, в `schema.py` — только после `_connect`).
  - Закрыто 2026-11-03: общий рецепт `schema.connect()`/`ensure_wal()` — для уже-WAL файла переключение пропускается, иначе повторяется с растущей паузой; используется в `server.py` и `on_message.py`. Регрессия: `test_56_concurrent_supervisors_vs_nonwal_writer` (6 supervisor под удерживаемой блокировкой записи; до фикса — все rc=4).

- [x] **P0-2. Проверить активацию новой версии listener в реальном окружении.**
  - Закрыто 2026-11-02: слушатель claude перезапущен штатно (disable → ожидание выхода по /proc → enable), новый pid, `status` отдаёт `stage=idle`; демо-задача прошла стадии `received → supervising → finished` с записью итога в `last` (`result=succeeded, duration_s=30.4`).
  - Остаток: сторона kimi — см. P1-12.

- [x] **P0-3. Добавить маркер версии/возможностей listener.**
  - Наблюдение: состояние `unknown` может означать и listener со старым кодом, и отсутствие доверенного progress-файла.
  - Нужно: добавить feature/version marker в status или progress-документ.
  - Критерий закрытия: status явно различает старую версию, отсутствие progress и ошибку чтения.
  - Закрыто 2026-11-03: реализация — cclocal (интерактивная сессия по дизайну msg#51 от kimi; headless-воркер ушёл в blocked по P1-11), ревью дифа, верификация и закрытие — kimi. progress-документ пишется с маркером `format_version: 2` (первым ключом); `status()` при живом pid различает `starting` (окно до первого flush, `STARTING_GRACE_SECONDS=60` по возрасту процесса из /proc), `legacy` (`missing_file` — старый listener без файла, или `no_format_version` — документ без маркера), `error` (`unreadable` — файл есть, не парсится), `unknown` (`stale_pid` — документ от чужого pid, проверяется раньше маркера; `last` из него по-прежнему показывается). Новый аддитивный ключ `progress_state` (null на нормальных стадиях); прежние поля не тронуты. Тесты: новый `test_63_status_stage_causes` (при слиянии с ревью-фиксами переименован из test_55) + правки test_47/48/52/53. Верификация kimi: `test_dispatcher.py` — ALL PASSED (49 тестов) дважды; штатный рестарт claude-listener (disable→/proc→enable, новый pid, `stage=idle`, документ с `format_version: 2`); живой старый kimi-listener честно показывает `stage=legacy`/`missing_file` (`[kimi] legacy`). Регрессии: `test_55_listener_delivers_after_deadline`, обновлённые `test_04`/`test_11`/`test_20`.

## Инварианты

- В логи, status и progress-файлы не попадают текст задачи, prompt, worker output, токены и другие секреты.
- Нет автоматических повторов неудачной попытки.
- Терминальное состояние conversation не принимает новые `task`/`result`.
- `auto.kimi` остаётся отключённым по умолчанию до явного решения пользователя.
- Рестарт слушателя — только внешняя операция (disable → выход процесса → enable); из диспетчеризованного воркера он архитектурно невозможен (мёртвая петля ожидания).
